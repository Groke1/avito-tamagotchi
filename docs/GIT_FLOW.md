# 🚀 Git Flow & Регламент разработки

Этот документ описывает единые правила работы с кодом и репозиторием в нашей команде на время хакатона. Соблюдение этих правил поможет нам избежать конфликтов слияния (merge conflicts) и позволит менторам Авито оценить вклад каждого участника

---

## 🌳 Структура веток (Branching Strategy)

В репозитории используется схема разработки **GitHub Flow** вокруг единственной основной ветки `main`.

- **`main`** — **Основная стабильная ветка.** В ней находится проверенный, рабочий код MVP. Все фичи сливаются напрямую в `main` через Pull Request. _Коммитить напрямую в `main` строго запрещено!_
- **`feat/...`** — Ветки под разработку нового функционала (создаются от `main`).
- **`fix/...`** — Ветки под исправление багов (создаются от `main`).
- **`docs/...`** — Ветки для документации и конфигураций инфраструктуры (Docker, CI/CD).

---

## 🏷️ Правила именования (Naming Conventions)

### 1. Ветки

Каждая ветка привязывается к конкретному Issue из **GitHub Projects**.

Формат: `<тип>/issue-<номер>-<краткое-название-на-английском>`

> **Примеры:**
>
> - `feat/issue-1-api-contract`
> - `feat/issue-3-react-setup`
> - `fix/issue-12-cors-error`
> - `docs/issue-4-readme`

---

### 2. Коммиты (Conventional Commits)

Пишите короткие, понятные сообщения на английском с префиксом типа задачи.

> **Примеры:**
>
> - `feat: add user profile response model`
> - `fix: repair token expiration validation`
> - `docs: create git flow specification`

---

## 🔄 Пошаговый алгоритм работы (Lifecycle задачи)

### Шаг 1. Взять задачу на доске

1. Перейдите в **GitHub Projects** (`Avito Gamification Board`).
2. Перетащите нужную карточку из колонки `Ready for Dev` в `In Progress`.
3. Назначьте себя исполнителем (`Assignee`).

---

### Шаг 2. Создать ветку локально

Перед созданием новой ветки **всегда обновляйте локальный `main`**:

```bash
# Переключаемся на main и подтягиваем свежие изменения
git switch main
git pull origin main

# Создаем новую фича-ветку от актуального main
git switch -c feat/issue-12-backend-crud
```

---

### Шаг 3. Разработка и коммиты

Пишите код, делайте атомарные коммиты.

> ⚠️ **Перед отправкой:** обязательно убедитесь, что ваш код локально собирается и запускается без ошибок!

```bash
git add .
git commit -m "feat: implement create user endpoint"
```

---

### Шаг 4. Подготовка и отправка Pull Request (PR)

Перед тем как отправить PR, обязательно подтяните свежие изменения из `main` в свою ветку, чтобы избежать конфликтов при мердже:

```bash
# Находясь в своей фича-ветке:
git pull origin main

# Если возникли конфликты — разрешите их локально, затем:
git push origin feat/issue-12-backend-crud
```

📌 **Примечание про Merge-коммиты:** При разрешении конфликтов слияния оставляйте стандартное служебное сообщение Git (например, `Merge branch 'main' into feat/issue-12...`).

---

### Шаг 5. Открытие PR в GitHub

1. Зайдите в репозиторий на GitHub и нажмите **New Pull Request**.
2. **Базовая ветка (Base):** `main`
3. **Сравниваемая ветка (Compare):** Ваша ветка (например, `feat/issue-12-backend-crud`).
4. **Заголовок PR:** Пишем на английском
   _(Этот заголовок GitHub автоматически подставит в название итогового squash-коммита!)_
   > **Примеры:**
   >
   > - `feat: implement user endpoints`
   > - `fix: repair token expiration validation`
   > - `docs: update setup instructions`
5. **Описание PR:** Заполните лаконичный шаблон (можно на русском):

```md
## Что сделано:

- Реализован эндпоинт POST /api/v1/users
- Добавлена валидация входных данных

## Как проверить:

- Запустить сервер, отправить POST-запрос с телом {...} через Postman

## Скриншоты (для UI задач):

- Прикрепить скриншот

Closes #12
```

_(Пример: `Closes #12`. После вливания PR карточка на канбан-доске автоматически перейдет в колонку `Done`)._

---

### Шаг 6. Code Review и Мердж

1. Перетащите карточку задачи на доске в колонку `In Review`.
2. Запросите ревью у напарника по роли.
3. После получения **Approve** нажмите кнопку **Squash and Merge**.
   _(GitHub автоматически подставит правильный заголовок коммита из названия PR, и в `main` попадет один чистый коммит)._
4. Удалите ветку в GitHub после слияния (`Delete branch`) и очистите ее локально у себя:

```bash
git switch main
git pull origin main
git branch -d feat/issue-12-backend-crud
```
